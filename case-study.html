How to use these case studies

These are interview design exercises, not descriptions of any named company's private systems. Start by clarifying business outcomes, existing technology, non-functional requirements, regulatory obligations, and operational ownership. Then explain a phased design, integration choices, failure handling, and measurable success criteria.

Important: Public company and sector references support the business context and standards; they do not prove a company's internal architecture. The proposed Azure/.NET stacks below are candidate designs, not claims about any named organization's private systems or exact products. Keep NDA-protected details out of interviews.
Fit the installed estate Preserve systems of record and existing identity, network, integration, and operations platforms unless a migration has a measurable business case.
Choose Azure services by need Use .NET where it fits. Select App Service, VMs, Functions, or AKS according to runtime, control, portability, and operations—not because every workload should be containerized.
Keep AI bounded Apply AI to assistive workflows first. Protect sensitive data, preserve authorization, measure quality, and keep accountable people responsible for regulated or safety-critical decisions.

Reusable Azure and Microsoft ecosystem baseline

Treat this as a menu, not a reference design to impose on every client. A real architecture can connect Azure to Windows Server, Active Directory, SQL Server, SAP, Oracle, Salesforce, ServiceNow, Kafka / Confluent, enterprise API gateways, and observability tools already operated by the organization.

Common building blocks

  • Application and APIs: C#/.NET and ASP.NET Core; Azure App Service for suitable web/API workloads; Azure Functions for event-driven tasks; AKS only when Kubernetes control, portability, or workload density justifies its operating cost.
  • Identity and security: Microsoft Entra ID, existing Active Directory federation, managed identities, Key Vault, private connectivity, network segmentation, Defender for Cloud, and the customer's SIEM such as Microsoft Sentinel or Splunk.
  • Integration: API Management alongside existing Kong / Apigee gateways; Service Bus for durable business messaging; Event Hubs or an existing Kafka / Confluent platform for partitioned streams; Logic Apps / Data Factory where integration or data movement is the actual requirement.
  • Data and analytics: retain SQL Server, Oracle, SAP, or other authoritative operational systems as required. Use Azure SQL, PostgreSQL, ADLS Gen2, Databricks / Delta Lake, or Fabric only when workload, governance, and ownership fit.
  • Operations: Azure Monitor and Application Insights integrated with existing OpenTelemetry, Splunk, Datadog, Dynatrace, ITSM, incident, and change-management practices.

Example request path:

Existing enterprise identity → API gateway → .NET service or workload → existing system of record / broker → governed analytics → monitoring, audit, and recovery

Case 1 · BFSI

Retail and commercial banking with insurance servicing

Banking · Payments · Lending · Insurance

Scenario: A large financial group wants to simplify digital customer servicing across deposit accounts, payments, lending, and insurance policy / claim journeys. It has a long-lived core banking platform, separate policy and claims applications, a data center estate, and a growing set of partner APIs.

Operational realities and pain points

  • Core ledger, loan servicing, card processing, policy administration, and claims have different owners, release cycles, data models, and availability windows.
  • Balance and payment correctness matters more than a cosmetically uniform API. Retries, duplicate submissions, settlement, reversals, reconciliation, and idempotency need explicit treatment.
  • Customer identity, KYC / AML case management, fraud controls, consent, and audit evidence span channels and operational teams.
  • Existing systems can include SQL Server, Oracle, mainframe or vendor core platforms, Active Directory / Entra ID, commercial payment networks, CRM, and an enterprise service bus.

Proposed integration and Azure design

  • Start with a channel-facing ASP.NET Core API layer behind the existing gateway or Azure API Management; do not bypass core service contracts.
  • Use synchronous APIs for customer queries and carefully bounded commands; use Service Bus or the existing broker for durable workflows and Kafka / Confluent or Event Hubs for event streams, according to existing standards.
  • Introduce domain services incrementally. Keep the system of record authoritative; publish changes through an outbox or equivalent reliable event pattern rather than dual-writing unrelated databases.
  • Integrate Entra ID with existing workforce and customer identity platforms; apply least privilege, private network paths, Key Vault, and centralized audit / SIEM controls.
Candidate stack: C# / ASP.NET Core, App Service or AKS where justified, API Management or existing Kong / Apigee, Service Bus and existing Kafka / Confluent, retained core banking and policy systems, SQL Server / Oracle, Azure SQL only for bounded new services, Entra ID, Key Vault, Azure Monitor / OpenTelemetry, and existing CRM / ITSM.

AI opportunities and Microsoft-oriented stack

  • Document intake: classify and extract fields from loan or claim documents with Azure AI Document Intelligence; validate fields against deterministic rules and route exceptions to staff.
  • Fraud / AML investigation assistance: use Azure Machine Learning or an approved existing risk engine to prioritize patterns; let investigators review alerts and make accountable decisions.
  • Policy and procedure assistant: retrieval with Azure AI Search and an approved model endpoint; enforce entitlement-aware retrieval, citations, redaction, logging, and refusal when source material is missing.

Do not let a generative model post ledger entries, approve credit, settle payments, or make final coverage / claims decisions.

Success measures: payment duplicate and reversal rates, reconciliation breaks, API availability and p95 latency, account-service completion, claim / loan document rework, fraud investigation time, audit exceptions, and cost per transaction.
Interview angle: Explain how you modernize around a core system without destabilizing it. Discuss consistency, idempotency, orchestration, regulatory evidence, and which part you would explicitly leave unchanged in the first release.

Case 2 · BFSI

Capital markets, exchange data, and surveillance

Markets · Trading · Data · Risk

Scenario: A market operator or investment firm needs resilient ingestion and distribution of trades, quotes, reference data, and news, with a cloud analytics path for surveillance and reporting. This is a cloud-adjacent modernization case, not an assumption that latency-critical matching should move to a public cloud.

Operational realities and pain points

  • Feed handlers, order gateways, matching engines, risk checks, and market-data distribution have different latency and availability needs. Some core paths remain colocated or on tightly controlled infrastructure.
  • Event ordering is usually scoped to an instrument, partition, or source; a global total order is expensive and should not be assumed.
  • Feed gaps, duplicates, clock drift, late corrections, schema changes, market opens, and bursts require replay and reconciliation procedures.
  • Surveillance needs lineage from alert to source events, analyst disposition, model or rule version, and any resulting report.

Proposed integration and Azure design

  • Keep exchange connectivity and latency-critical order execution in the approved low-latency zone; use a controlled gateway to publish copies or derived events to enterprise streaming.
  • Use existing Kafka / Confluent or Event Hubs with partition keys, sequence checks, durable retention, and replay policies; never infer business-level exactly-once processing from broker delivery alone.
  • Land immutable, access-controlled raw events in ADLS Gen2; curate analytics in Databricks / Delta Lake or an established lakehouse, and serve operational dashboards separately from transaction systems.
  • ASP.NET Core services can provide analyst workflows, case APIs, and reference-data access; integrate with the existing surveillance, execution, identity, and records platforms.
Candidate stack: Existing feed handlers and exchange connectivity; C#/.NET services for workflow and control plane, with native or vendor components retained for latency-critical paths; Kafka / Confluent or Event Hubs, ADLS Gen2, Databricks / Delta Lake, SQL Server for bounded workflow data, Entra ID, Key Vault, private networking, OpenTelemetry, and the firm's current surveillance and market-data products.

AI opportunities and Microsoft-oriented stack

  • Surveillance triage: anomaly models can rank alerts for human review using Azure Machine Learning or the existing model platform; preserve reproducible features, rule versions, and analyst outcomes.
  • Research retrieval: Azure AI Search over licensed filings, approved research, and internal procedures, with document entitlements and source citations.
  • Operations support: summarize feed-health and incident evidence for on-call teams, without allowing an LLM to alter orders, market data, or surveillance dispositions.
Success measures: feed completeness, sequence-gap detection time, event lag, p99 analytics latency, replay success, surveillance alert precision / review time, lineage completeness, and cost per billion events processed.
Interview angle: Explain how you separate a deterministic execution path from an asynchronous analytics path. State the ordering scope, replay design, and failure behavior during a market-data burst or regional outage.

Case 3 · Healthcare

Large healthcare payer and care operations

Payer · Provider · Claims · Care

Scenario: A large healthcare payer and care-services organization needs to improve member and provider workflows across eligibility, claims, prior authorization, and care coordination.

Operational realities and pain points

  • Payer and provider workflows exchange eligibility, claim, authorization, remittance, clinical, and identity data with different ownership and processing timelines.
  • Real estates commonly combine commercial claims platforms, provider systems / EHRs, SQL and document databases, batch extracts, X12 transactions, APIs, and older HL7 interfaces.
  • Data must be purpose-limited and access-controlled. Minimum necessary, consent, retention, identity matching, and auditability are design concerns, not a final deployment checklist.
  • Eligibility and authorization decisions depend on current policy, clinical context, benefits, and human workflow; stale or mismatched records can cause rework and member harm.

Proposed integration and Azure design

  • Keep claims and policy systems of record authoritative. Add ASP.NET Core façade APIs and workflow services incrementally behind existing API management and identity controls.
  • Use Azure Health Data Services FHIR where the use case and FHIR version fit; bridge existing HL7 v2 and X12 EDI via approved integration engines or partners rather than assuming they are replaced by FHIR.
  • Separate PHI-bearing operational paths from analytical workloads using classified storage, managed identities, encryption, private connectivity, controlled de-identification, and auditable access.
  • Integrate with existing EHR, claims adjudication, pharmacy benefit, CRM, provider directory, and call-center platforms. Track provenance and reconciliation across asynchronous exchanges.
Candidate stack: ASP.NET Core, Azure API Management or the existing gateway, Azure Health Data Services FHIR where appropriate, existing HL7 / X12 integration services, Service Bus for workflow commands, existing Kafka / Event Hubs for analytics events, SQL Server / claims platforms retained as systems of record, ADLS Gen2 and Databricks / Fabric for governed analytics, Entra ID, Key Vault, private networking, Azure Monitor / Sentinel, and organization-approved de-identification services.

AI opportunities and Microsoft-oriented stack

  • Prior-authorization packet assistance: use Azure AI Document Intelligence to extract requested fields and missing documents; present evidence to qualified reviewers rather than making an automated denial.
  • Call-center and care-team retrieval: use Azure AI Search and an approved model endpoint to summarize entitlement-filtered policy material with source citations and PHI-safe logging.
  • Claims operations: use validated ML to identify duplicate or anomalous submissions for investigation. Keep adjudication rules deterministic, auditable, and governed by the organization's authorized process.
Success measures: eligibility response success, claim rework and reconciliation, prior-authorization cycle time, provider data match rate, member call resolution, FHIR / X12 interface errors, PHI access exceptions, and reviewer override rates.
Interview angle: Describe how you preserve the payer's system of record while enabling interoperable APIs. Explain authorization propagation, PHI boundaries, interface retries, and why FHIR does not remove existing X12 and HL7 integration needs.

Case 4 · Healthcare & Pharma

Global pharmaceutical manufacturing operations

Manufacturing · Quality · Supply

Scenario: A global pharmaceutical manufacturer wants better visibility across plants, laboratory systems, quality events, serialization, and distribution. This scenario does not assert that any specific company uses the proposed Azure stack or has a particular internal deficiency.

Operational realities and pain points

  • Plant operations combine MES / batch records, LIMS, QMS, ERP such as SAP, historians, equipment vendor systems, warehouse management, and serialization services. Interfaces may be site-specific and validated on separate release cycles.
  • A batch has controlled master data, material genealogy, equipment state, process parameters, quality checks, and release decisions. Data lineage and time synchronization matter during deviations and investigations.
  • Electronic records, signatures, audit trails, validated changes, retention, segregation of duties, and controlled access must align with applicable GxP and jurisdictional requirements.
  • Serialization and product traceability link manufacturing, packaging, logistics partners, markets, and exception resolution. Connectivity and partner standards vary by region.

Proposed integration and Azure design

  • Leave validated MES, LIMS, QMS, ERP, and plant control systems authoritative. Integrate through supported vendor interfaces, message queues, APIs, or controlled batch exchange.
  • Use an OT/IT boundary with segmented plant networks and an edge gateway; buffer telemetry locally through site outages. Do not put cloud connectivity in the safety or deterministic control loop.
  • Stream approved events to Event Hubs or the existing Kafka platform. Land governed analytics copies in ADLS Gen2 and an established Databricks / Fabric environment; keep the validated source record clear.
  • Implement change control, environment segregation, validation evidence, replay procedures, and plant-by-plant rollout rather than a big-bang global cutover.
Candidate stack: .NET APIs and integration workers where appropriate, Azure Arc-enabled edge Kubernetes / Azure IoT Operations only after OT suitability review, OPC UA / MQTT adapters, existing SAP / MES / LIMS / QMS, Service Bus for controlled workflows, Kafka / Event Hubs for telemetry, ADLS Gen2, Databricks / Delta Lake or the current enterprise data platform, Entra ID, Key Vault, private network links, and controlled audit storage.

AI opportunities and Microsoft-oriented stack

  • Equipment maintenance: analyze non-GxP or appropriately validated sensor history using Azure Machine Learning or the existing analytics platform to rank inspection needs; a technician approves work.
  • Quality deviation search: retrieve approved SOPs and historical deviation / CAPA records using Azure AI Search and an approved model endpoint. Keep access restricted, cite source records, and require quality-unit review.
  • Visual inspection support: assess whether computer vision can flag defects for trained operator review. Validate the model, equipment, drift controls, and intended use before considering any production quality decision.

Do not let an LLM change a batch record, release a product, approve a deviation, or sign a regulated record.

Success measures: batch-record completeness, deviation investigation time, approved system change lead time, serialization exceptions, historian-to-analytics delay, equipment downtime, validation defects, and audit-trail review completion.
Interview angle: Explain how you add analytics without changing the validated source of truth. Discuss validation scope, electronic signatures, data integrity, plant outage buffering, and controlled deployment.

Case 5 · Energy

Oil and gas production, midstream, and refining

Oil & Gas · Industrial IoT

Scenario: An integrated energy company needs operational visibility across remote assets, pipelines, terminals, and processing facilities. Relevant, verifiable energy and industrial-IoT experience can anchor the interview story where disclosure is permitted; this architecture remains generalized and is not a claim about a specific company or site.

Operational realities and pain points

  • Field assets produce telemetry through PLCs, RTUs, SCADA, historians, meters, and vendor protocols such as Modbus; facilities may also expose OPC UA or MQTT at integration boundaries.
  • Remote connectivity is intermittent and bandwidth constrained. Operations teams need local alarming, operator HMI, and deterministic control to keep functioning if cloud connectivity fails.
  • Production accounting, nominations, pipeline measurement, maintenance, work orders, safety, and environmental reporting are handled in separate OT and business systems.
  • Asset tag naming, units, timestamps, quality flags, and vendor-specific semantics are often inconsistent. Poor normalization makes enterprise dashboards misleading.

Proposed integration and Azure design

  • Preserve PLC / RTU and SCADA control locally. Use segmented OT zones and a read-only, governed edge integration path for cloud telemetry where practical.
  • Normalize tags, units, timestamps, and quality metadata at the edge; buffer and forward with sequence / gap tracking. Keep historian retention and plant historian tools in place.
  • Use Azure IoT Operations on Azure Arc-enabled Kubernetes only where the site can support the operating model; bridge MQTT / OPC UA or existing vendor gateways to Event Hubs / Kafka.
  • Integrate work orders and asset master data with SAP / EAM / CMMS; publish governed data to ADLS Gen2 and Databricks / Fabric for reliability and production analytics.
Candidate stack: Existing SCADA, PLC/RTU, historian (for example AVEVA PI where already deployed), Modbus / OPC UA / MQTT edge adapters, Azure Arc and Azure IoT Operations where fit, Event Hubs or existing Kafka, .NET APIs for enterprise asset and work-order integration, SAP / CMMS, ADLS Gen2, Databricks / Delta Lake, Entra ID for workforce access, and Azure Monitor / existing OT monitoring.

AI opportunities and Microsoft-oriented stack

  • Predictive maintenance: use Azure Machine Learning or a current industrial analytics platform to rank compressor / pump inspection risk using historian trends and maintenance outcomes.
  • Alarm and shift-handover summaries: retrieve authorized operations procedures and summarize alarm context through Azure AI Search and an approved model endpoint; an operator verifies any action.
  • Leak / anomaly triage: correlate sensor deviations, pressure, flow, and maintenance history to prioritize inspection. Safety instrumented systems and emergency shutdown logic remain independent and deterministic.
Success measures: telemetry completeness, edge buffering and recovery, time to detect sensor gaps, alarm acknowledgement, unplanned downtime, maintenance work-order completion, false-positive rate, and operator acceptance.
Interview angle: Describe where the OT trust boundary sits, how the site behaves during a WAN outage, and why cloud AI may recommend inspection but must not replace local control or safety interlocks.

Case 6 · Energy

Renewable generation and power-grid operations

Wind · Solar · Storage · Grid

Scenario: A utility or independent power producer wants a unified operational data and forecasting layer across wind, solar, storage, and grid-connected assets. The control-room and market-dispatch systems remain authoritative; analytics support operators rather than silently changing dispatch.

Operational realities and pain points

  • Assets combine plant controllers, inverter telemetry, SCADA, meters, weather services, market schedules, work management, outage management, GIS, and sometimes DERMS / EMS platforms.
  • Generation is variable and forecast error has commercial and reliability impacts. Weather, telemetry, asset availability, curtailment, and grid constraints need time-aligned data.
  • Interconnection and grid operations use utility-specific protocols and approved operational procedures; bulk electric system assets may have additional NERC reliability and cybersecurity obligations.
  • Distributed sites may have intermittent connectivity. A cloud outage must not remove local protection, control, or operator visibility required by the site.

Proposed integration and Azure design

  • Keep protection relays, plant control, EMS / SCADA commands, and market dispatch in their approved control systems. Treat cloud as supervisory analytics and enterprise integration.
  • Use edge gateways for approved read-only telemetry, time synchronization, local buffering, and normalization; connect across segmented OT boundaries with least privilege.
  • Stream telemetry and weather / schedule data to Event Hubs or the existing Kafka platform; persist time-series and curated history in the organization's chosen historian and lakehouse.
  • Join asset, outage, weather, and market data for fleet analytics. Integrate with existing GIS, OMS, EAM, billing, and regulatory reporting rather than replacing them wholesale.
Candidate stack: Existing plant SCADA / EMS / DERMS / OMS / GIS, approved DNP3 / IEC 61850 / OPC UA gateways, Azure Arc and Azure IoT Operations for edge data where appropriate, Event Hubs / Kafka, .NET APIs for asset and work management, ADLS Gen2, Databricks / Delta Lake or Fabric for analytics, Azure Machine Learning, Entra ID, Key Vault, private links, and operational monitoring integrated with utility practices.

AI opportunities and Microsoft-oriented stack

  • Renewable generation forecasting: combine approved weather forecasts, asset state, and historical generation using Azure Machine Learning or an existing energy forecasting product; expose confidence intervals and model drift.
  • Asset health: rank wind turbine, inverter, or battery maintenance risks using validated telemetry features and work-order history; route recommendations to operations.
  • Outage and curtailment analysis: summarize event sequences and likely contributing factors for operator review using Azure AI Search and an approved model endpoint over authorized records.

Keep automated setpoints and grid-protection decisions in approved control systems with engineered safety and change controls.

Success measures: forecast error by horizon, asset availability, telemetry freshness, curtailment analysis time, maintenance lead time, false alarms, control-room adoption, and recovery behavior during communications outages.
Interview angle: Explain time alignment, forecast uncertainty, edge buffering, OT segmentation, and the boundary between decision support and control.

Case 7 · Telecom

Telecom OSS/BSS modernization and network operations

5G · OSS · BSS · Customer operations

Scenario: A communications provider wants to improve service provisioning and network assurance while integrating multiple generations of network equipment and long-running business support systems.

Operational realities and pain points

  • OSS covers inventory, service assurance, fault, configuration, and network orchestration; BSS covers product catalog, order capture, rating, billing, customer care, and partner settlement. The two sides share customer, service, and resource data but often have different owners.
  • Provisioning spans CRM, order management, inventory, workflow, and vendor network controllers. Stale inventory or partial completion can leave customer orders stuck or services inconsistently configured.
  • Radio, core, transport, cloud, and vendor-specific telemetry produce high-volume alarms and metrics. Correlation must distinguish a common underlying fault from many downstream symptoms.
  • Network changes require approved maintenance windows, rollback plans, service impact assessment, and operations-center visibility; autonomous configuration is not the default safe assumption.

Proposed integration and Azure design

  • Use TM Forum Open APIs or the provider's established API contracts to reduce point-to-point coupling; maintain explicit versions and compatibility testing.
  • Implement order orchestration as durable stateful workflows with idempotent activities, timeout handling, compensation, and manual repair queues for partial provisioning.
  • Retain vendor EMS / NMS, network controllers, inventory, and billing systems as authoritative where they are established. Integrate telemetry via Kafka / Confluent or Event Hubs.
  • Run suitable .NET control-plane APIs on App Service or AKS based on workload needs; use private connectivity for operator and OSS integration and separate customer-facing systems from network-management planes.
Candidate stack: ASP.NET Core, API Management or existing gateway, TM Forum Open APIs, Service Bus / existing workflow engine for order state, Kafka / Confluent or Event Hubs for telemetry, SQL Server / Oracle and OSS/BSS products retained as systems of record, ADLS Gen2 / Databricks for analytics, Entra ID, Key Vault, Azure Monitor / OpenTelemetry and the carrier's existing NOC / ITSM tools.

AI opportunities and Microsoft-oriented stack

  • Alarm correlation: cluster related alarms and rank likely causes using Azure Machine Learning or the provider's existing AIOps tooling; show supporting topology and telemetry to a network engineer.
  • Service desk assistance: retrieve approved runbooks and incident history with Azure AI Search and an approved model endpoint, with citations and access controls.
  • Capacity forecasting: predict cell, transport, or edge demand with time-series models; engineers review planned capacity and configuration changes.
Success measures: order fallout, time to provision, service inventory consistency, mean time to detect / repair, alarm noise ratio, customer-impact minutes, API compatibility, and change-related incidents.
Interview angle: Describe how you handle a partial order failure across a CRM, service inventory, and network controller. Explain the workflow state, compensation or repair process, and operational ownership.

Case 8 · Retail

Omnichannel retail inventory and order fulfillment

Stores · E-commerce · Supply chain

Scenario: A national retailer wants a more reliable inventory and order view across stores, e-commerce, distribution centers, and suppliers. Customers expect pickup, ship-to-home, returns, and accurate delivery promises, while the enterprise must preserve existing ERP, POS, and warehouse operations.

Operational realities and pain points

  • POS, e-commerce, OMS, ERP, WMS, merchandising, supplier EDI, loyalty, and payment systems update on different schedules and often have different product and location identifiers.
  • Inventory is a changing estimate: reservations, in-flight shipments, returns, shrink, substitutions, cancellations, and late store events affect available-to-promise.
  • Peak events create burst traffic, hot SKUs, inventory contention, slow downstream suppliers, and queue backlogs. Order capture should not imply fulfillment until inventory and policy checks succeed.
  • Card data should remain with approved payment providers and tokenization flows; operational analytics and AI must not expand payment scope unnecessarily.

Proposed integration and Azure design

  • Keep ERP / OMS as explicitly selected systems of record. Publish inventory and order events through an outbox or controlled integration layer, with idempotent consumers.
  • Use ASP.NET Core services for bounded APIs and order workflow; use Service Bus for durable order commands and Kafka / Event Hubs for high-volume inventory and clickstream streams where the existing platform supports them.
  • Use SQL Server / Azure SQL for transactional workloads only where its consistency and scale fit; use Redis or another cache for transient reads with explicit staleness and invalidation rules.
  • Integrate suppliers through existing EDI / API partners and normalize product identifiers, GTINs, locations, and event timestamps before analytical use.
Candidate stack: .NET / ASP.NET Core, Azure API Management or current gateway, Service Bus for order commands, Kafka / Confluent or Event Hubs for inventory events, retained POS / ERP / OMS / WMS, SQL Server / Azure SQL for suitable transactional components, Redis for bounded cache use, ADLS Gen2 and Databricks / Fabric for demand and operations analytics, Entra ID, Key Vault, Azure Monitor, and existing payment tokenization provider.

AI opportunities and Microsoft-oriented stack

  • Demand and replenishment: forecast SKU / store demand using Azure Machine Learning or an existing forecasting platform; show confidence and allow planners to account for promotions, holidays, and supply constraints.
  • Product discovery and service: use Azure AI Search for hybrid product search and an approved model endpoint for grounded customer-service answers; respect product availability, locale, and published policy.
  • Operations exception triage: summarize delayed orders, supplier notices, and inventory mismatches from authorized records. Require a human decision before financial adjustment, refund, or supplier commitment.
Success measures: inventory accuracy, order cancellation / substitution rates, promise accuracy, fulfillment cycle time, queue age, peak p95 latency, return reconciliation, and payment-data scope.
Interview angle: Explain what “available inventory” means, how reservations and duplicate events are handled, and what the customer sees if OMS or a store is temporarily disconnected.
